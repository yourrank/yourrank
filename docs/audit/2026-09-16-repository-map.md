## Auth, data, and configuration ownership

* **Creator sessions/auth:** `apps/leaderboard/src/auth.js`, `handlers/auth.js`, `packages/shared/src/session.ts`, OAuth state/safe-next helpers. Session state is stored in Postgres rather than KV.
* **Viewer sessions/auth:** `handlers/viewer-auth.js`, `viewer-session.ts`, `oauth-state.ts`, Kick/Discord OAuth helpers, and `site-render.ts`. Provider flags are site data (`viewerKickAuthEnabled`, `viewerDiscordAuthEnabled`); renderer selects Kick, then Discord, then generic `/me` based on those flags.
* **Public viewer/community data:** `site-data.js`, `site-routes.js`, `handlers/public.js`, `site-render.ts`; membership and credits are community-scoped.
* **Rewards/claims:** `handlers/credits.js`, `handlers/claims.js`, reward pages/assets, and migrations for rewards, code drops, images, claims/redemptions, and durable mutation operations.
* **Support/feedback:** `pages/help.js` + editable `assets/contact.js` call `handlers/contact.js`; `support_messages` are stored before optional email notification. Notification failure is logged as a warning, so durable receipt and inbox delivery are separate states. Feedback is handled separately by `handlers/feedback.js`/viewer modal.
* **Consent:** `assets/cookie-consent.js` writes `yr_consent` to localStorage and a first-party cookie; current UI exposes only “Essential only” and “Accept all,” with no ordinary preferences editor/footer control.
* **Relevant migrations:** support messages/replies/tickets, viewer feedback/dashboard, site members, OAuth states, session rotation, worker-login RLS, activity automation, reward images/keys, Polar billing, viewer-session authority, and durable mutation operations under `supabase/migrations/` (timestamps 20260711 through 20260915).
* **Deployment config:** production domain is `yourrank.site`, session cookie domain `.yourrank.site`; production binds R2 reward images, `MARKETING`, Queues, Durable Objects, and a five-minute Leaderboard cron. Config does not identify the deployed SHA.
